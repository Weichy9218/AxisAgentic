01整体分层：核心库和配方的分工

代码分成两半。agentic/ 是与任务无关的运行时，不知道 BrowseComp 是什么；recipe/ 是具体任务包，自带配置模型、提示词、数据集、判分器和产物格式。想加一个新任务族，做法是在 recipe/ 下新建一个自包含的包，而不是改核心库。

图 1。左边是代码分层，右边是产物流向。所有下游都从同一份 trace 出发，这是整个框架的中心假设。

四条替换点写在文档里，也确实是接口：实现 agentic.tools.base.Tool 加工具，实现 agentic.model_clients.base.ModelClient 换传输层，继承 ConversationRuntime 或 TaskOrchestrator 换控制策略，实现 datasets 和 evaluation 的契约接新基准。

02一次任务怎么跑完：会话状态机

大多数 agent 框架的主循环是一个 while，里面用 if 判断该调模型还是该调工具。AxisAgentic 把这个循环提成了一个显式状态机，放在 agentic/contracts/conversation.py。它有 15 个具名阶段（ConversationStage），一张合法转移表（VALID_STAGE_TRANSITION），以及一个只有三个值的对外动作枚举（StepAction：调模型、执行工具、结束）。编排器只对这三个值分发，不去 pattern match 具体阶段。

图 2。三条非正常路径都不删历史。回滚只是插一条标记消息，说明"从这里往前隐藏 N 条"，完整记录留在 trace 里。

这个设计带来的直接后果是，模型看到的对话不等于记录下来的对话。ConversationRuntime 同时维护两份：full_conversation 是只追加的完整记录，visible_conversation 是把所有标记应用一遍之后的结果。三种标记定义在 agentic/contracts/markers.py，第 5 节会展开。

回滚的六种原因是有枚举的（RollbackReason）：上下文触顶、模型拒答、工具调用格式错误、重复查询、工具报错、生成 token 耗尽。每种在 trace 里可分辨，所以事后能统计"这个模型在这个基准上主要是被哪类问题卡住"。

03工具层

3.1 一个工具是什么

agentic/tools/base.py 里的 Tool 抽象基类只要求实现一个方法 arun(arguments, context) -> ToolResult。构造参数除了名字、描述、JSON Schema 之外，还带着执行策略：

构造参数作用
strict_mode是否在工具定义里加 strict: true。搜索抓取这些工具全部设为 False，因为它们的 schema 不满足 strict 模式对 additionalProperties 的要求。
server_nameMCP 风格的分组名。list_server_tool_groups() 按它把工具聚成"服务器"，用于渲染成 MCP 形态的系统提示。
max_calls_per_task这个工具在单个任务里的调用上限。
max_consecutive_calls_with_same_args连续多少轮用完全相同的参数调它就拒绝。搜索和抓取工具默认是 2。
call_budget_exceeded_message
consecutive_call_exceeded_message		被拒绝时回给模型的话。可以按工具定制，因为模型看到不同措辞会改变后续行为。
emoji写进工具 trace，仪表盘和日志里用它区分工具类型。

返回值 ToolResult 有四个字段。content 是唯一进入模型上下文的部分。status 分三档，SUCCESS、FAILED、REJECTED，其中 REJECTED 表示工具压根没执行（配额、未知工具名、连续同参），FAILED 表示执行了但出错。reason 是原因枚举。metadata 只进 trace，不进上下文。

metadata 里的数字会被 ToolManager 自动采样成指标。顶层数值直接采，一层嵌套的数值用下划线拼接成扁平键。键名里含 _ms 的下游会额外生成一个 _seconds 别名。如果 metadata 里有 request_latency_ms，还会自动合成 client_queue_ms = 总耗时 - 请求耗时，用来区分"后端慢"和"客户端排队"。写工具时只要往 metadata 里塞数字，指标就有了。

四种工具形态覆盖了不同来源：

CallableTool

包一个普通的同步或异步函数。它会按函数签名过滤掉多余的参数，所以模型多传了字段不会直接抛 TypeError。from_mcp_definition() 可以直接吃 MCP 的 {name, description, inputSchema}，让系统提示里的渲染结果和真 MCP 服务器一致。

MCPToolAdapter

把调用转发给外部执行器，带一个 backend_name。这是接真 MCP 服务器的位置。

OrchestratorTool

把一整个 TaskOrchestrator 包成工具，也就是子 agent。注册时 ToolManager 会把嵌套层级 level 和调用路径 tool_path 传下去，于是子 agent 的日志能标出自己在第几层、经由哪条路径被调用。

直接继承 Tool

需要持有跨调用状态时用。基类留了 begin_task 和 end_task 两个生命周期钩子，代码沙箱就靠这两个钩子管理沙箱的创建和销毁。

3.2 ToolManager 的执行流水线

模型发来的每个工具调用要穿过七道关卡才会真正执行。这七道关卡的顺序是固定的，写在 agentic/tools/manager.py 的 _execute 里。

图 3。被拒绝的调用不计入任务总调用数，但会计入指标里的 num_rejected，所以"模型被挡了多少次"是可统计量。

几个容易忽略但影响实际行为的细节：

  • 连续同参是跨轮次比较，不是轮内比较。execute_tool_calls 一次调用算一轮。本轮成功执行的参数会替换上一轮的记录，本轮没被调用的工具计数清零。所以"连续两轮搜同一个词"会被拦，"这一轮搜两次同样的词"不会。
  • 拒绝消息是给模型看的文案。默认文案是"本次工具调用未执行，因为该工具在本任务的调用配额已用尽"这类。工具可以覆盖它，因为不同的措辞会导致模型选择换工具还是直接收尾。
  • 任务状态可以快照和恢复。snapshot_task_state() 和 restore_task_state() 把调用计数、连续同参记录、指标一起存取。重试和分支（比如 attempt budget sweep 的分叉）靠这两个方法保证配额不会串。
  • 指标每个任务重置。reset_task_state() 会清空累计指标，避免跨任务污染。

3.3 参数修复器

agentic/tools/argument_repair.py 处理的是模型把参数名写错、类型写错的情况。默认关闭，需要在配置里显式打开，而且默认跳过 strict 模式的工具（因为 strict 模式下 endpoint 本该已经保证了格式）。打开后按固定顺序跑五条规则：

规则做什么
normalize_key_names去掉键名首尾的空白和引号。模型偶尔会生成 "\"query\"" 这样的键。
schema_aliases读 schema 里的自定义字段 x-agentic-aliases，把别名改写成正名。这是在 JSON Schema 里挂扩展键的做法，写工具时可以给 query 声明别名 q、search_query。
fuzzy_property_match只在恰好有一个多余键和恰好一个缺失属性时才动手，用 SequenceMatcher 算相似度，超过 0.72 才改。条件卡得很死，是为了避免猜错。
schema_defaults把 schema 里声明了 default 但模型没传的字段补上，并且会先检查默认值本身是否符合声明的类型。
scalar_type_coercion字符串 "10" 转成整数 10，"true" 转成布尔。只做标量，不碰对象和数组。

规则不够用时可以按工具注册自定义钩子（register_argument_repair_hook）。修复过的请求会在 metadata.argument_repair.applied_rules 里留下用了哪几条规则，所以事后能统计模型的参数错误率，而不是让修复把问题掩盖掉。

3.4 参数顺序守卫

agentic/tools/schema_order.py 解决的是一个不太常见但真实存在的问题。工具参数的顺序由 Python 字典的插入顺序决定，模型在系统提示里看到的顺序会影响它的生成。有些 chat template 在渲染 JSON 时会排序键名，于是提示里的参数顺序和代码里的不一致，而这种漂移不会报错，只会让效果悄悄变差。validate_rendered_tool_argument_order() 拿渲染完的提示文本和工具定义比对，顺序变了就报错。

04工具清单与每个工具的内部处理

Web Search 配方注册的工具很少，只有搜索、抓取，以及可选的代码沙箱。工具少是有意的，系统提示里明确写了每轮只调一个工具。

工具 模型看到的参数 后端 内部做的事
🔍 web_search query 必填；num、gl、hl、location、time_range、page 可选。另有精简版 schema 只暴露前四个。 Serper Google Search 指数退避重试，只重试连接错误、超时和配置的状态码，不再重试所有 4xx。查询带双引号且返回空结果时，自动去掉引号重试一次。过滤基准答案泄漏源（HuggingFace 数据集和 spaces 页面）。对返回 URL 做保守的百分号解码，保留 RFC 3986 保留字符不动。metadata 记录每次尝试的耗时、原始条数、过滤条数、是否用了去引号重试。
📄 jina_scrape url 必填，custom_headers 可选。 Jina Reader，失败回退直连 HTTP 先按 Content-Type 路由，服务端返回 JSON、CSV、XML 这类结构化数据时直接取原文，因为 Jina 会把数据接口渲染成空的 HTML 表单。HTML 和 PDF 走 Jina。Jina 失败则用浏览器 UA 直连 HTTP 重试。同样过滤封禁 URL。返回内容按 max_content_length 截断（配置默认 409600 字符）。metadata 分段记录探测、Jina、回退各自的耗时和实际用了哪个后端。
🧠 llm_extract content 和 info_to_extract 都必填。 独立的抽取用 LLM endpoint 长文本走分块 map-reduce。single 策略是每块抽一遍再一次归并，recursive 策略是把归并结果继续递归压缩直到放得下。块之间有重叠字符防止跨块信息丢失。抽取缓存默认关闭，因为落盘缓存的文件锁和 fsync 在高并发下会拖慢客户端。
🌐 scrape_and_extract_info url 必填，info_to_extract 和 custom_headers 可选。 组合上面两个 不重复实现，直接调用两个子工具的内部函数。多一层原始抓取缓存，键是 URL、请求头、Jina 基址、长度上限的 sha256，可选做 URL 归一化（小写 scheme 和 host，query 排序）。只有成功且非空的结果才入缓存，失败和空内容记为 bypass 并标注原因。info_to_extract 为空时返回全文，非空时返回抽取结果。
🐍 python_exec code E2B 沙箱 默认关闭。有状态的解释器，变量、导入、函数在整个任务尝试内保持。
💻 shell_exec cmd 同一个 E2B 沙箱 默认关闭。和 python_exec 共用文件系统和包环境，所以 shell 装的包能直接 import，任一边写的文件另一边能读。系统提示里明确要求不要把 Python 源码丢进 shell_exec。

4.1 抓取工具的内部路径

图 4。抓取的每一步都记了耗时，所以 trace 里可以区分"Jina 慢"和"抽取用的 LLM 慢"，这在调并发时有用。

4.2 代码沙箱的会话作用域

python_exec 和 shell_exec 不是两个独立沙箱，而是共享一个 SessionScopedCodeExecutionRuntime。这个运行时的生命周期挂在 Tool.begin_task 和 Tool.end_task 上：

  • 沙箱是惰性创建的，第一次调代码工具才建。只用搜索和抓取的任务完全不占 E2B 配额。
  • 每次执行前刷新沙箱超时，长任务不会中途被回收。
  • E2B 返回 429 时按退避策略等待重试，而不是把限流错误当成工具结果回给模型（否则模型会以为是自己代码写错了）。
  • 遇到"沙箱不存在"错误会先销毁再重建，然后重试。
  • 任务结束时 end_task 杀掉沙箱。ToolManager 是按注册顺序倒序调 end_task 的。
  • metadata 里带 sandbox_id、sandbox_scope、e2b_retries，跨任务的沙箱问题可追。

05值得单独说的设计

5.1 三种上下文标记，一套回放规则

这是整个框架里最特别的一点。长程 agent 迟早会撞上下文上限，常见做法是直接改历史（截断、替换、摘要）。AxisAgentic 不改历史，改的是"怎么从历史算出可见对话"。三种标记都是 role=ConversationRuntime 的消息，带一个 JSON payload。

图 5。三种标记的解析和拼接函数都在 agentic/contracts/markers.py 一个文件里。运行时求可见对话、离线回放、trace 查看器、SFT 导出，四条路径共用这一套函数。

markers.py 的文档注释把这件事说得很直白：这个模块是两种格式的唯一所有者，生产者、在线回放、离线回放和测试都必须走这些函数，这样在线的提示推导和持久化 trace 的重建不可能漂移。这是"状态忠实"这个说法的实际含义，SFT 导出的样本里不会包含当时对模型隐藏的历史，也不会包含已被回滚的动作。

标记解析函数对 payload 做了严格校验，包括显式拒绝布尔值（因为 Python 里 bool 是 int 的子类，prefix_len: true 会被当成 1）。范围放不下时返回 None，调用方当作无操作，而不是抛异常或者猜一个位置。

5.2 上下文管理的三条路线

配置里这三条是互斥或者分层的关系，不是叠加。

路线触发条件行为与代价
依赖 provider 报错默认 模型端点返回上下文超长错误，或 finish_reason=length 运行时不做本地 token 预检，省掉每轮的估算开销，适合高并发。出错后走 generation_limit_recovery：非最后一次尝试直接结束本次尝试用外层重试配额，最后一次尝试反复回滚较早的助手和工具往返再重新生成。
本地估算预检 每次调模型前算一遍剩余预算 估算器有三种，cheap 是按字符数的增量估算并用 provider 报的 input_tokens 校准，chat_template 用真 tokenizer 更准但长对话下有客户端延迟。适合 provider 不会可靠拒绝超长请求的情况。
周期性压缩 每 interval 个助手回合压一次，保留最近 recent_window 个回合原文 需要单独的压缩模型 endpoint。压缩提示词要求输出九个固定键的 JSON，包括已确认事实、当前假设、已否决路径、答案候选、冲突候选、搜索状态、重试策略。输出格式不合法会带着具体错误重试一次并提高 token 上限。
清空重开 上次模型调用的 prompt 用量超过上下文窗口的 trigger_ratio（默认 0.80） 比压缩更激进，直接丢掉全部工具历史让模型重新开始。有 min_turns_between 防抖，还有一个不随清空重置的全局工具调用上限（默认 1800）。和压缩互斥，且要求上下文检测模式必须是 provider 报错，两条都是启动时强制检查。

5.3 答案抽取与自我验证

答案约定是 \boxed{}。extract_boxed_content 是手写的括号匹配，处理转义和嵌套，取最后一个 boxed 内容，并且有一个黑名单过滤掉 ?、...、unknown 这类无效答案。没闭合的 boxed 也会尽力取到文本末尾。

自我验证默认开启。模型给出 boxed 答案之后，用同一个模型带工具再验证一遍（上限 300 轮）。判定为错就重新作答，最多三次，每个新答案再验证一遍。裁决输出解析不了时会重新采样最多三次，还是解析不了才当作不正确。验证和重答都跑在候选模型上，不需要额外的验证器 endpoint。

还有一个兜底：如果最终什么都没抽出来，会去找中途出现过的 boxed 答案，或者从压缩摘要的 answer_attempts 里捞。这条兜底始终开着，所以高预算的长跑不会因为收尾时刻的意外而交白卷。

5.4 尝试预算扫描

attempt_budget_sweep_enabled 打开后，一次 rollout 会同时产出多个预算档位的产物。运行目录本身对应最大预算，attempt_budget_<B> 子目录对应 1 到 max_task_retries 的各个档位，每个档位报告"最多允许 B 次尝试"时的正确率。这样"重试几次划算"这个问题只需要跑一遍，不用跑 N 遍。实现上靠的是编排器在关键位置做状态快照和分叉（_snapshot_attempt_mutable_state 和 _run_attempt_budget_final_branch_from_checkpoint）。

5.5 推理内容的保留

配置里 preserve_reasoning_content 默认开启，作用是把助手的 reasoning_content 回放进后续的模型请求。不同模型家族对历史 thinking 的处理方式不一样，配置文件里给了四家的 request_extra_body 示例，分别控制各自 chat template 里"是否清除历史 thinking"和"下一次生成是否进入 thinking 模式"。这些开关只影响发给 endpoint 的内容，trace 里的 content、reasoning_content 和工具调用始终是结构化分开存的。对做轨迹采集来说，这一条决定了导出的样本里有没有推理过程。

06和 galaxy 怎么比

6.1 先看清两者是什么

galaxy 是 Milkyway-Harness-Agent 里的预测 agent 研究运行时。它自己写了 ReAct 循环、工具层、MCP 客户端和上下文管理。它的核心约束是预测任务特有的：在 T_cut 时刻事件还没发生，答案不可检索，只有可外推的信号可检索。这条约束决定了它的大部分设计。

AxisAgentic 的核心约束不一样：它要在多个搜索基准上跑出可比较的分数，并且把跑出来的轨迹变成能训练的数据。这条约束决定了它的大部分设计。

图 6。同一行不代表功能对等，只表示在各自体系里处在相近的位置。最下面一行是双方最不对称的地方。

终止条件 抽 \boxed{}。预算触顶时追加收尾提示强制要一个答案。没有 boxed 就用兜底路径去历史里捞。 自然终止。模型发出不带工具调用的消息就是终止，那条消息本身就是最终答案，没有 finalize 工具。强制停止时追加一次无工具的收尾调用，仍没有 boxed 就记 schema_miss。
工具协议 进程内 Tool 抽象。可以从 MCP 定义构造，也可以适配到外部 MCP 执行器，但默认工具都跑在同一个进程里。 真 MCP 服务器（FastMCP，导入期用装饰器注册），加上 harness 层的进程内内置文件工具。工具模块导入失败会被 catch，那个模块的工具静默不注册。
工具可见性 注册即可见，没有额外的白名单层。要减工具就少注册，配置里有 disable_all 做纯模型基线。 profile 的 tool_set 决定哪些工具对 agent 可见。另有一层运行时参数剥离，T_cut、search_provider、time_window、domains 从模型看到的 schema 里去掉，模型无法设置信息边界。
工具配额 四层：单轮上限、任务总上限、单工具上限、连续同参上限。拒绝有原因枚举并进指标。 一个全局 max_tool_calls，加软死线和上下文预算比例。内置文件工具不计入工具预算。
工具结果的表示 两份。content 进上下文，metadata 进 trace 并被采样成指标。 三份，返回值、审计记录、模型可见投影，三者可以合法地不一致。文档明确说泄漏审计必须查投影，查返回值会漏。
证据存储 证据全在对话里。页面内容进上下文之前先被抽取或截断，超长了靠压缩或清空。 抓到的东西全保真落盘，模型按需读有界切片。read_artifact 有七种切片模式，重复读同一份返回一个指针而不是内容。搜索摘要落盘是全文，给模型的副本裁到 200 字符。
上下文管理 回滚、压缩、清空三种标记，可见对话从完整记录推导出来。 双轨记录，完整审计 jsonl 加一份压缩后的上下文视图，两份分别维护。另有悬空工具调用清理和字符阈值截断。
回放 标记回放，在线求可见对话和离线回放共用一套函数，这是设计目标之一。 session jsonl 支持断点续跑。另有离线回放审计，冻结早期 notebook 重放后期推理，用来区分收益来自 harness 适配还是网页内容漂移。
跨任务记忆 没有。include_failure_summary 只在同一任务的多次尝试之间传失败摘要。 核心机制。F/E/U 三轴的 (axis, WHEN, guidance) 三元组，问题内通道在结果揭晓前跨 checkpoint 对比自己的笔记，跨问题通道在揭晓后聚类合并写进 SKILL.md。有确定性的质量闸（每轴最多 5 条、同轴 Jaccard 重叠超 0.75 拒绝）。
时间边界 只有系统提示里的一行日期，可以固定也可以取当天。搜索工具会过滤基准答案泄漏源，但没有时间维度的过滤。 整套契约。T_cut 由 end_time − delta_days 推导，provider 层编码（Exa 用 end_published_date，Serper 用 tbs=cdr），客户端 as-of 守卫再筛一遍，只排除已证明晚于截止的证据，无日期的admit 并标 unknown。文档同时明确说这是卫生层不是隔离层，并给了实测的泄漏比例。
评测 LLM judge（默认判 5 次）加 DeepSearchQA 的 macro F1、WideSearch 的 item F1。有 Streamlit 仪表盘做实验对比和逐条轨迹检查。 每题一个 [0,1] 的分数，跨题型取简单平均。用 Brier、相对误差、校准曲线。有专门的配对规则和"绝不编造概率"的约束。
训练闭环 有。Swift Agent 格式的 SFT 导出，导出前按标记重放可见性；另有一个小的 rollout facade 对接外部训练系统。 没有 SFT 导出。改进走提示词侧的自进化，不动模型权重。
子 agent 有接口没在用。OrchestratorTool 能把编排器包成工具并传递层级和调用路径，但参考配方里没有注册子 agent。 在用。sub_agent_factor 和 sub_agent_access 在 main toolset 里，有独立的子 agent 提示词。
边界约束方式 靠包结构和文档约定。核心库不 import recipe。 靠测试强制。workbench 和 harness 都不许 import galaxy.forecast，用 AST 遍历检查。

6.3 三种比法，成本递增

第一种，机制清单对照

成本接近零，应该先做。把上面那张表当作 checklist，逐条问三个问题：对方有我没有的机制是什么，我有对方没有的是什么，同一件事两边的做法差在哪。这一步的产出不是分数，是一份"可以互相借的东西"的清单。目前看下来比较明显的两条：

  • AxisAgentic 可以借 galaxy 的证据落盘加有界切片。现在页面内容要么进上下文要么丢掉，抽取失误就没有第二次机会。落盘之后模型可以换一个角度重读同一份材料，也不再需要为了省上下文而在抽取时激进裁剪。
  • galaxy 可以借 AxisAgentic 的标记式可见性推导。它现在是双轨维护完整记录和压缩视图，两份分开维护就有漂移的可能。改成从完整记录推导视图之后，离线回放审计的可信度会更高，而这个审计恰好是它论文里的关键论据。

第二种，受控的同基准实验

要出分数就得让两边跑同一批题。方向的选择上，把 galaxy 拿来跑 BrowseComp 比反过来便宜。原因是 AxisAgentic 已经有 BrowseComp 的 loader 和官方判分器，galaxy 那边只需要写一个 benchmark adapter 并把 temporal_policy 设成 disabled_control（它本来就有这个不做时间过滤的对照臂）。反方向要在 AxisAgentic 里实现 T_cut 推导、三层强制、as-of 标注和 Brier 评分，工作量大得多。

必须对齐的变量：

变量怎么对齐
模型和 endpoint同一个服务地址、同一个模型 id、同样的 temperature 和 top_p。两边都要检查 thinking 相关的 extra_body 是否等价，这一项不对齐会直接改变行为。
搜索后端都用 Serper，同一个 key。galaxy 的 search_provider 设 serper。
抓取后端都用 Jina。galaxy 的浏览器渲染升级路径要么关掉，要么在报告里作为差异项单独说明。
工具调用上限AxisAgentic 的 max_turns 加 ToolManager 配额，对齐到 galaxy 的 max_tool_calls。注意 galaxy 的内置文件工具不计预算，这一条对不齐，要在报告里写明。
上下文窗口两边填同一个数值，并且都要确认这个数值和 endpoint 实际能用的一致。
判分用同一个判分器、同一个判分模型、同样的判分次数。AxisAgentic 的 judge 默认判 5 次，galaxy 那边要接同一套。
题目集与顺序同一个 jsonl，同一个 shuffle seed，或者干脆关掉 shuffle。

对不齐而且不应该强行对齐的：工具粒度本身。galaxy 有 notebook、read_artifact、浏览器工具、金融数据工具，AxisAgentic 只有搜索加抓取加可选沙箱。这个差异是被测的东西，不是噪声。硬要把 galaxy 的工具砍到只剩两个，测出来的就不是 galaxy 了。正确做法是把两边的工具清单原样列在报告里。

该看的指标不止正确率：

  • 正确率，以及正确率的置信区间（题目少的时候差几个点可能没有意义）。
  • 每题工具调用数和每题 prompt token 总量。这两个决定成本，正确率相同但成本差一倍是重要结论。
  • 上下文触顶率。AxisAgentic 有 context_limit 回滚原因的计数，galaxy 有 STOP_CONTEXT_BUDGET 的停止原因。
  • 终止原因分布。AxisAgentic 的六种回滚原因和四种终止阶段，galaxy 的六种 stop reason，这两组能大致对上。
  • 无答案率。AxisAgentic 的空 boxed 兜底触发次数，galaxy 的 schema_miss。
比之前先跑一遍双方的冒烟配置确认环境没问题。galaxy 的 README 明确说了它的环境必须用 .venv-test 且要带 env -u PYTHONPATH PYTHONNOUSERSITE=1 前缀，uv run 在那台机器上会卡住。AxisAgentic 用 ./setup_env.sh 加 .envs/axis_agentic_env.sh，并且支持 --dry-run 先验证配置。两边环境不干净的话，测出来的差异可能只是环境差异。

第三种，组件级移植实验

如果目的是搞清楚"某个机制值多少分"而不是"哪个系统更好"，最干净的做法是在同一个系统内部做消融，而不是跨系统比。比如想知道证据落盘值多少，就在 AxisAgentic 里加一个落盘加切片读的工具，其他全不变，跑同一批题看差值。想知道 F/E/U 记忆值多少，galaxy 已经有 NH、GH、ACE、FH 加逐轴消融的矩阵可以直接用。

跨系统比出来的差值包含了几十个未受控变量，很难归因到某一个机制上。同系统消融的差值归因清楚，代价也低得多。除非目的就是"选一个系统来用"，否则第三种比第二种更值得做。

6.4 有一条根本不该比

两个系统的任务范式不同。搜索问答的答案存在于网上，能不能答对取决于找不找得到、认不认得出。预测的答案在提问时还不存在，正确性来自外推。galaxy 的文档里专门用一节说明混淆这两者是它最贵的一类错误，58% 的题目曾经卡在纯检索模式里反复改写查询。所以"哪个 agent 更强"这个问题在跨范式的意义上没有答案，只有"在某个具体基准上，控制住这些变量之后，差多少"这样的问题有答案。
